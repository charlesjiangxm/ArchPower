# Event-Only Dataset Generation

## Overview

This document describes how the **event-only dataset** is generated by the script
`src/build_event_dataset.py`. The goal is to produce a transformed dataset where
power labels are **independent of hardware parameters** and depend only on
**workload (event) variation**.

The transformation is based on the **resource functions** defined in the PANDA
power model ([PANDA.py](../src/PANDA.py)), which capture the dominant
hardware-driven scaling of each CPU component's power consumption. By dividing
out this hardware-dependent factor, the remaining label captures only the
event-driven power behavior.

---

## Background: The ArchPower Dataset

The original [ArchPower](../../README.md) dataset contains **200 samples** collected
from two CPU architectures:

| Architecture | Configs | Workloads per config | Total samples |
|---|---|---|---|
| BOOM | 15 | 8 | 120 |
| XiangShan (XS) | 10 | 8 | 80 |

Each sample has:

- **Features** (`feature.npy`): a 101-dimensional vector combining **20 hardware
  parameters** (constant within a config) and **81 event parameters** (varying
  across workloads).
- **Labels** (`label.npy`): reshaped to `(200, 12, 5)`, where:
  - Dimension 1 (12): `[Total, BP, ICache, IFU, RNU, LSU, DCache, Regfile, ISU, ROB, FU-Pool, Others]`
  - Dimension 2 (5): `[total_power, combinational_logic, sequential_logic, memory, clock]`

Within any single configuration group (8 samples), the hardware parameters are
identical — only the event parameters change across the 8 workloads. This means
the raw power labels carry **two entangled sources of variation**: hardware
configuration and workload behavior.

---

## Motivation

For downstream tasks that want to study **how workload behavior affects power**
— independent of which hardware configuration is being used — we need to
**factor out** the hardware-dependent component from the power labels.

PANDA's resource functions provide exactly this decomposition. PANDA models each
component's power as:

$$P_c = R_c(\mathbf{x}_{\text{hw}}) \cdot f_c(\mathbf{x}_{\text{event}})$$

where:
- $R_c(\mathbf{x}_{\text{hw}})$ is the **resource function** — a closed-form
  expression of hardware parameters that captures the dominant scaling
- $f_c(\mathbf{x}_{\text{event}})$ is the **event-dependent residual** learned
  by a machine learning model (XGBoost in PANDA)

By computing:

$$P'_c = \frac{P_c}{R_c(\mathbf{x}_{\text{hw}})}$$

we obtain a **hardware-normalized** power value that should be comparable across
different configurations.

## Step-by-Step Generation Process

### Step 1: Load Raw Data

The script loads three types of data:

1. **Global features** — `dataset/feature.npy`, shape `(200, 101)`
2. **Labels** — `dataset/label.npy`, reshaped to `(200, 12, 5)`, then sliced
   at `power_group=0` (total power) to get shape `(200, 12)`
3. **Per-component features** — 11 files from `dataset/component_feature/`,
   one per component:

| Component | File | Shape | Feature range (in concatenated matrix) |
|---|---|---|---|
| BP | `BP.npy` | (200, 6) | [0, 6) |
| ICache | `ICache.npy` | (200, 11) | [6, 17) |
| IFU | `IFU.npy` | (200, 21) | [17, 38) |
| RNU | `RNU.npy` | (200, 11) | [38, 49) |
| LSU | `LSU.npy` | (200, 5) | [49, 54) |
| DCache | `DCache.npy` | (200, 14) | [54, 68) |
| Regfile | `Regfile.npy` | (200, 8) | [68, 76) |
| ISU | `ISU.npy` | (200, 6) | [76, 82) |
| ROB | `ROB.npy` | (200, 4) | [82, 86) |
| FU-Pool | `FU-Pool.npy` | (200, 4) | [86, 90) |
| Others | `Others.npy` | (200, 101) | [90, 191) |

> **Note:** `Others.npy` is identical to `feature.npy` — it is the full
> 101-dimensional architecture-level feature vector, not a small residual block.

### Step 2: Split by Architecture

The 200 samples are split:
- **BOOM**: samples 0–119 (15 configs × 8 workloads)
- **XS**: samples 120–199 (10 configs × 8 workloads)

Each architecture is processed independently to produce its own output files.

### Step 3: Identify Event-Only Features

For each column in `feature.npy`, we check whether it is **constant within every
configuration group** (groups of 8 consecutive samples). If it is constant, it is
a **hardware parameter**; otherwise, it is an **event parameter**.

This yields:
- **20 hardware features** (indices: 0–13, 33, 34, 60, 61, 63, 64)
- **81 event features** (all remaining indices)

Only the 81 event features are retained in the output feature matrix.

### Step 4: Apply Resource Functions to Labels

For each of the 11 components, a **resource function** $R_c(\mathbf{x}_{\text{hw}})$
is computed from the component's hardware features, and the raw power label is
divided by this factor.

The resource functions are defined in the `encode_table` from
[DataLoader.py](../src/DataLoader.py) and the `encode_arch_knowledge()` function
in [PANDA.py](../src/PANDA.py). The indices in the table below are **local** to
each component's feature file:

| Component | Resource Function $R_c$ | encode_table indices | Formula |
|---|---|---|---|
| **BP** | Multiplicative | [0] | $R = x_0$ |
| **ICache** | Multiplicative | [3, 4] | $R = x_3 \cdot x_4$ |
| **IFU** | Multiplicative | [1] | $R = x_1$ |
| **RNU** | Multiplicative | [1] | $R = x_1$ |
| **LSU** | Multiplicative | [0] | $R = x_0$ |
| **DCache** | Multiplicative | [0, 1] | $R = x_0 \cdot x_1$ |
| **Regfile** | Additive | [1, 2] | $R = x_1 + x_2$ |
| **ISU** | Structured lookup | [0] | $R = \text{RS\_entries}(x_0)$ |
| **ROB** | Multiplicative | [1] | $R = x_1$ |
| **FU-Pool** | Identity (none) | — | $R = 1$ (no transformation) |
| **Others** | Multiplicative | [1] | $R = x_1$ |

**Detailed explanation of each type:**

#### Multiplicative (BP, ICache, IFU, RNU, LSU, DCache, ROB)

For these 7 components, the resource function is a product of one or two
hardware features:

$$R_c = \prod_{i \in \text{encode\_table}[c]} x_i$$

These features have been verified to be hardware parameters (constant within
each config group). The physical intuition is that component power scales
roughly linearly (or bilinearly) with these structural parameters. For example:
- **ICache**: power scales with `nSets × nWays` (indices 3, 4)
- **DCache**: power scales with `nSets × nWays` (indices 0, 1)
- **BP**: power scales with the branch predictor table size (index 0)

#### Additive (Regfile)

The register file power scales with the **sum** of two register-count features:

$$R_{\text{Regfile}} = x_1 + x_2$$

This reflects that register file power is proportional to the total number of
physical registers (integer + floating-point).

#### Structured Lookup (ISU)

The Issue Unit's power scales with the total number of reservation station
entries, which is a non-trivial function of `decodeWidth`:

$$R_{\text{ISU}} = \text{RS\_entries}(\text{decodeWidth})$$

The lookup table maps `decodeWidth` to reservation station entries:

| decodeWidth | IQT_MEM | IQT_INT | IQT_FP | Total RS entries |
|---|---|---|---|---|
| 1 | 8 | 8 | 8 | 24 |
| 2 | 12 | 20 | 16 | 48 |
| 3 | 16 | 32 | 24 | 72 |
| 4 | 24 | 40 | 32 | 96 |
| 5 | 24 | 40 | 32 | 96 |

#### Identity (FU-Pool)

FU-Pool has **no entry** in the `encode_table`, so no resource function is
applied. Its raw power label is kept as-is in the transformed dataset.

#### Others

The Others component uses a single hardware feature as the scaling factor. In
the original PANDA code, there is an attempt to estimate a bias term
(`logic_bias`) via linear regression, but due to a Python scoping issue (the
local variable assignment inside `estimate_bias_logic()` does not update the
module-level variable), the bias is effectively **0** at runtime. Our
implementation faithfully replicates this behavior:

$$R_{\text{Others}} = x_1 + 0 = x_1$$

### Step 5: Compute Transformed Total Power

After transforming all 11 per-component labels, the **total transformed power**
is computed as their sum:

$$P'_{\text{total}} = \sum_{c=1}^{11} P'_c = \sum_{c=1}^{11} \frac{P_c}{R_c(\mathbf{x}_{\text{hw}})}$$

> **Note:** This transformed total is **not** the same as dividing the raw total
> power by a single resource function. Each component is normalized by its own
> hardware-dependent scale, then the normalized values are summed. The physical
> interpretation is a "hardware-normalized power intensity."

### Step 6: Save Output

The outputs are saved as NumPy files in `dataset/event_dataset/`:

```
dataset/event_dataset/
├── BOOM_event_feature.npy    # (120, 81) — event features only
├── BOOM_event_label.npy      # (120, 12) — [total, 11 components]
├── XS_event_feature.npy      # (80, 81)  — event features only
└── XS_event_label.npy        # (80, 12)  — [total, 11 components]
```

**Label columns:**

| Index | Name | Description |
|---|---|---|
| 0 | Total | Sum of transformed component powers |
| 1 | BP | Branch Predictor |
| 2 | ICache | Instruction Cache |
| 3 | IFU | Instruction Fetch Unit |
| 4 | RNU | Rename Unit |
| 5 | LSU | Load/Store Unit |
| 6 | DCache | Data Cache |
| 7 | Regfile | Register File |
| 8 | ISU | Issue Unit |
| 9 | ROB | Reorder Buffer |
| 10 | FU-Pool | Functional Unit Pool |
| 11 | Others | Other Logic |

## Validation

The generated dataset was validated against several criteria:

### Shape Correctness

| Architecture | Feature shape | Label shape |
|---|---|---|
| BOOM | (120, 81) ✅ | (120, 12) ✅ |
| XS | (80, 81) ✅ | (80, 12) ✅ |

### Internal Consistency

- `label[:, 0] == sum(label[:, 1:12])` — max absolute difference: **0.0** ✅
- No NaN or Inf values in features or labels ✅

### Hardware Scaling Removal

Taking BP (Branch Predictor) on BOOM as an example, the per-config mean power
shows that hardware-dependent variation has been successfully factored out:

**Raw BP power (varies with hardware config):**

| Config | Mean power (W) |
|---|---|
| 0 | 0.2082 |
| 1 | 0.2092 |
| 2 | 0.2090 |
| 3 | 0.2021 |
| 4 | 0.2104 |

**Transformed BP power (hardware-independent):**

| Config | Mean power (normalized) |
|---|---|
| 0 | 0.0520 |
| 1 | 0.0523 |
| 2 | 0.0523 |
| 3 | 0.0505 |
| 4 | 0.0526 |

The raw power varies by a factor determined by the BP table size (the hardware
parameter), while the transformed power is comparable across configs — the
remaining variation is driven purely by workload differences.

## Usage

To regenerate the dataset:

```bash
cd src
python build_event_dataset.py
```

To load the dataset in your own code:

```python
import numpy as np

# Load BOOM event dataset
feat = np.load('dataset/event_dataset/BOOM_event_feature.npy')   # (120, 81)
label = np.load('dataset/event_dataset/BOOM_event_label.npy')    # (120, 12)

# Event features for all samples
X = feat  # shape (120, 81) — only event parameters

# Per-component transformed power
total_power = label[:, 0]
bp_power    = label[:, 1]
icache_power = label[:, 2]
# ... etc.
```

## Relationship to PANDA

This transformation corresponds to the **encoding** step (`encode_arch_knowledge`)
in `src/PANDA.py`. In PANDA's full modeling pipeline:

1. **Encode**: divide component power by $R_c(\mathbf{x}_{\text{hw}})$
   → hardware-normalized label
2. **Train**: fit an XGBoost model on the normalized label using component features
3. **Predict**: XGBoost predicts the normalized power for unseen samples
4. **Decode**: multiply prediction by $R_c(\mathbf{x}_{\text{hw}})$ to recover
   actual power

Our event-only dataset captures the output of **step 1** — it is the
hardware-normalized representation that PANDA's ML models learn from. The key
difference is that we also **strip hardware features** from the feature matrix,
leaving only the 81 event dimensions, so the entire dataset is
hardware-parameter-free.
